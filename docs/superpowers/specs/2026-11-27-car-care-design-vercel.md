## 0. 이 문서에 대해

### 0.1 목적
**비교용** 설계 문서다. "마이카노트를 처음부터 Vercel 에 배포한다고 가정하면 설계가 어떻게 달라지는가"를 정리한다. 실제 구현은 Cloudflare 버전으로 진행 중이며, 이 문서는 기존 코드를 옮기는 이전(migration) 계획이 **아니다**.

서비스 내용(기능 · 계산 로직 · 화면 · 알림 규칙)은 Cloudflare 버전과 **같다**. 달라지는 것은 실행 환경, DB, 예약 작업, 캐시, 비밀값 보관, 배포 흐름이다. 비교할 때 차이가 플랫폼에서만 나도록 ORM(Drizzle) · 인증(Auth.js) · 스타일 · 테스트 도구는 일부러 같게 두었다.

### 0.2 한눈에 보는 차이

| 영역 | Cloudflare 버전 | Vercel 버전 (이 문서) |
|---|---|---|
| 실행 | Next.js → **vinext** 로 빌드 → Workers | **순정 Next.js** → Vercel Functions (Node.js 런타임) |
| DB | D1 (SQLite), Worker 바인딩 | **Neon Postgres** (Vercel Marketplace 연동), 연결 문자열 |
| ORM · 마이그레이션 | Drizzle (sqlite) + cf CLI 로 적용 | Drizzle (pg) + `drizzle-kit migrate` 를 **빌드 단계**에서 적용 |
| 예약 작업 | Cron Trigger → `scheduled()` (`src/worker.ts` 로 진입점 감쌈) | **Vercel Schedules** → 보호된 HTTP 경로 호출 (진입점 감쌀 필요 없음) |
| Web Push | `@block65/webcrypto-web-push` (Web Crypto) | **web-push** (Node 표준 라이브러리) |
| 외부 API 캐시 | Workers Cache API (`caches.default`) | **Next.js 데이터 캐시** (`fetch` 의 `revalidate`) |
| 비밀값 | Worker Secret + `.dev.vars` | **Vercel 환경 변수** (Production / Preview / Development 별) + `.env.local` |
| 배포 (CD) | GitHub Actions 가 검사 → 마이그레이션 → 배포 | **Vercel Git 연동**이 배포. GitHub Actions 는 검사만 |
| PR 프리뷰 | 빌더 재량(선택) | **PR 마다 자동** + Neon **DB 브랜치** 자동 생성 |
| 테스트 DB | `node:sqlite` + 같은 마이그레이션 SQL | **PGlite**(WASM Postgres) + 같은 마이그레이션 SQL |
| 무료 플랜 제약 | D1 · Workers 무료 한도 | Vercel Hobby(**비상업 용도**), Schedules 실행 오차 15분, Neon 저장 공간 한도 |

### 0.3 Vercel 버전을 고르면 얻는 것과 잃는 것 (요약)
- 얻는 것: vinext 호환 위험이 사라진다(순정 Next.js). PR 마다 앱 + DB 프리뷰가 자동으로 생긴다. Node 생태계 라이브러리(`web-push`, `pg` 등)를 그대로 쓴다. 진입점을 감싸는 등의 플랫폼 우회 코드가 없다.
- 잃는 것: DB 가 앱 밖(Neon)에 있어 연결 관리와 지연(왕복)이 생긴다. 무료 플랜의 예약 작업 시각이 정확하지 않다. CD 가 GitHub Actions 가 아니라 Vercel 안에서 돌아, "배포 자동화를 직접 짰다"는 포트폴리오 포인트가 약해진다(대신 프리뷰 DB 브랜치 흐름을 보여준다).
- 자세한 비교와 선택 이유는 17장.

## 1. 개요

### 1.1 한 줄 정의
사용자가 자기 차량과 주행 습관을 등록하면, **"내 차는 지금 무엇을 언제 정비해야 하는가"**를 자동으로 계산해 알려주고, 필요한 순간에 근처 정비소·부품 최저가·관련 소식으로 연결해주는 웹 서비스.

### 1.2 왜 만드는가 (의도)
- **포트폴리오용** 프로젝트다. 프론트엔드뿐 아니라 백엔드(DB, 서버 로직, 예약 작업, 외부 API 연동, 배포 자동화)까지 혼자 설계·구현했다는 것을 보여주는 것이 목적이다.
- 가짜(목업) 데이터가 아니라 **실제 데이터를 최대한** 사용한다.
- 리뷰어(면접관·채용 담당자)가 가장 먼저 봐야 할 부분은 **"내 차에 맞춘 정비 시기 추천"과 "알림"**이다. 나머지 기능(지도, 최저가, 뉴스)은 이 핵심 흐름을 보조한다.

### 1.3 핵심 차별점
1. **주행거리 자동 추정** — 사용자가 매번 주행거리를 입력하지 않아도, 일 평균 주행거리로 오늘의 주행거리를 추정한다.
2. **실측 기반 보정** — 정비 기록·계기판 입력이 쌓이면 실제 주행 패턴을 계산해 추정치를 스스로 교정하도록 제안한다.
3. **차량별 규칙** — 연료 타입(가솔린/디젤/LPG/하이브리드/전기)에 따라 정비 항목과 주기가 달라진다. (예: 전기차는 엔진오일 없음)
4. **기능 간 연결** — 알림 → 정비 항목 상세 → "근처 정비소 지도" / "이 부품 최저가" 로 이어지는 하나의 흐름.

## 2. 목표 · 비목표 · 안티골

### 2.1 목표 (Goals)
- G1. 차량 등록 후 **3분 안에** 사용자가 자기 차의 정비 현황 대시보드를 본다.
- G2. 정비 시기가 다가오면 사용자가 사이트를 열지 않아도 **Web Push 알림**을 받는다.
- G3. 주행거리 추정 → 정비 시기 계산 → 알림 발송까지의 로직이 **서버에서 직접 작성한 코드**로 존재하고, 단위 테스트로 검증된다.
- G4. 지도·최저가·뉴스 데이터는 **실제 외부 API**(카카오, 네이버)에서 가져온다.
- G5. 배포가 자동화되어 있다: GitHub Actions 로 CI(검사·테스트·빌드), **Vercel Git 연동**으로 CD(main → 운영, PR → 프리뷰 + 프리뷰 DB 브랜치), 배포 후 스모크 테스트.
- G6. 리뷰어가 **로그인 없이도** 핵심 흐름을 체험할 수 있다(데모 모드).

### 2.2 비목표 (Non-goals) — 이번 4주에는 하지 않는다
- 네이티브 모바일 앱 (웹 + PWA로 충분)
- 실제 차량(OBD, 커넥티드카) 연동으로 주행거리 자동 수집
- 정비소 예약·결제, 쇼핑 결제
- 다나와 등 공식 API가 없는 사이트 크롤링
- 커뮤니티·리뷰·댓글 기능
- 관리자(어드민) 페이지 — 규칙·차종 데이터는 시드(seed) 파일로 관리
- 다국어

### 2.3 안티골 (Anti-goals) — 동작하더라도 이렇게 되면 실패
- 기능 다섯 개가 **각자 따로 노는 링크 모음**처럼 보이는 것. (핵심은 "내 차 맞춤"이다.)
- 정비 주기를 **공식 권장값처럼 단정**하는 것. 참고용 수치임을 화면에 명시해야 한다.
- 알림이 **스팸처럼** 반복 발송되는 것. 같은 내용은 한 번만 보낸다.
- 포트폴리오로 걸어둔 뒤 몇 달 지나 **조용히 고장 나는 것**(예약 작업 중단, API 키 만료로 빈 화면). 외부 API 실패 시에도 화면은 깨지지 않아야 한다.
- 데모를 보려면 **소셜 로그인부터 해야 하는 것**.

## 3. 사용자와 핵심 시나리오

### 3.1 대상 사용자
- 차량을 1대 보유한 일반 운전자. 정비 주기를 잘 모르고, 보통 "경고등이 뜨거나 정비소에서 말해줘야" 정비한다.
- (포트폴리오 관점) 리뷰어: 5분 안에 서비스의 핵심과 기술적 깊이를 파악하고 싶다.

### 3.2 시나리오 가 — 처음 방문한 운전자
1. 랜딩 페이지에서 "내 차 등록하기"를 누른다.
2. 카카오 또는 구글로 로그인한다.
3. 제조사 → 모델 → 연식 → 연료를 선택한다. (예: 현대 / 아반떼(CN7) / 2021 / 가솔린)
4. 현재 계기판 주행거리를 입력한다. (예: 42,000km)
5. **주행 습관 계산기**로 일 평균 주행거리를 정한다. (예: 출퇴근 편도 18km × 주 5일 + 주말 이틀 합계 40km → (180 + 40) ÷ 7 ≈ 일 평균 31km)
6. (선택) 최근 정비 이력을 입력한다. 모르면 "기억 안 남"을 선택한다.
7. 대시보드에 항목별 정비 현황과 예상 시기가 나타난다.
8. "정비 시기가 되면 알려드릴까요?" → 알림 허용.

### 3.3 시나리오 나 — 3주 뒤 알림을 받은 운전자
1. 휴대폰에 "엔진오일 교체 시기가 다가와요 (약 500km 남음)" 푸시가 온다.
2. 알림을 누르면 엔진오일 상세 화면이 열린다.
3. "근처 정비소 보기"를 누르면 현재 위치 기준 지도에 정비소가 표시된다.
4. 또는 "엔진오일 최저가 보기"를 누르면 네이버 쇼핑 최저가 목록이 나온다.
5. 정비를 마친 뒤 "정비 완료"를 누르고 계기판 주행거리를 입력한다. → 다음 교체 시기가 새로 계산되고, 주행거리 기준점이 보정된다.

### 3.4 시나리오 다 — 포트폴리오 리뷰어
1. 랜딩 페이지에서 "데모로 둘러보기"를 누른다.
2. 미리 준비된 데모 차량(정비 기록과 주행 기록이 쌓인 상태)으로 대시보드에 들어간다.
3. 보정 제안 카드, 계절 정비 카드, "교체 필요" 상태 항목을 바로 본다.
4. 대시보드의 "테스트 알림 받기" 버튼으로 실제 푸시 알림을 받아본다(구독 정보는 저장되지 않음, 4.4).

## 4. 기능 명세

우선순위: **P0** = 핵심, 반드시 완성 / **P1** = 연결 기능, 가볍게 완성 / **P2** = 시간이 남으면

### 4.1 P0 — 핵심 기능

#### 가. 로그인 / 데모 모드
- 소셜 로그인: 카카오, 구글 (Auth.js).
- 데모 모드: 로그인 없이 읽기 전용 데모 계정으로 진입. 데모 데이터는 시드로 생성하며, 데모 계정에서의 수정은 막는다(또는 세션 종료 시 버려지는 임시 사본 — 빌더 재량, 4.4 참고).
- 회원 탈퇴 시 해당 사용자의 모든 데이터(차량, 기록, 구독, 알림)를 삭제한다.

#### 나. 차량 등록·관리
- 입력: 제조사, 모델, 연식, 연료 타입, 별명(선택), 현재 주행거리, 기준 날짜(기본: 오늘).
- 제조사·모델 목록은 서비스가 보유한 **차종 시드 데이터**에서 고른다. 목록에 없으면 "기타"를 고르고 모델명을 직접 입력하며, 연료 타입만으로 규칙을 적용한다.
- MVP는 **사용자당 차량 1대**를 기본 화면으로 다룬다. 데이터 모델은 여러 대를 허용하도록 설계한다(화면상 차량 전환은 P2).

#### 다. 주행 습관 계산기
- 입력 방식 두 가지 중 선택:
  - (a) 직접 입력: 일 평균 km 또는 월 평균 km (월 → 일 환산: ÷ 30.4)
  - (b) 계산기: (출퇴근 편도 거리 × 2 × 출근 일수/주 + 주말 이틀 합계 거리) ÷ 7 → 일 평균(반올림). 예: (18 × 2 × 5 + 40) ÷ 7 = 31.4 → 31km
- 결과: 일 평균 km(정수 반올림)와 월 평균 km를 보여주고, **일 평균만** 저장한다(월 평균은 표시용 계산값).
- 유효 범위: 일 평균 1 ~ 500km. 범위를 벗어나면 입력을 거부하고 이유를 알려준다.

#### 라. 주행거리 추정
- 공식: `추정 주행거리(오늘) = 마지막 실측 주행거리 + 일 평균 km × (오늘 − 마지막 실측일)의 일수`
- "실측"은 사용자가 직접 입력한 계기판 값(등록 시, 정비 완료 시, 수동 업데이트 시)이다.
- 추정값은 저장하지 않고 **요청 시 계산**한다. (저장하는 것은 실측값과 일 평균뿐)
- 화면에는 추정값 옆에 "추정" 표시와 마지막 실측일을 함께 보여준다. (예: "약 42,775km · 11/1 실측 기준")
- 대시보드에 "계기판 값 업데이트" 버튼을 둔다.

#### 마. 정비 규칙 엔진
- 각 정비 항목은 **거리 주기(km)**와 **기간 주기(개월)** 중 하나 또는 둘을 가진다. 둘 다 있으면 **먼저 도달하는 쪽**이 기준이다.
- 규칙은 연료 타입별로 적용 여부와 주기가 다르다. (6장 규칙 테이블)
- 항목별 계산 결과:
  - 마지막 교체 시점(주행거리·날짜) — 정비 기록이 있으면 그것, 없으면 "기준점"(7.3 참고)
  - 다음 교체 시점: `마지막 교체 km + 주기 km`, `마지막 교체일 + 주기 개월`
  - 남은 거리, 남은 기간
  - **예상 도래일**: 거리 기준 예상일(`오늘 + 남은 km ÷ 일 평균`)과 기간 기준일 중 빠른 날
  - 진행률(%) = max(거리 진행률, 기간 진행률)
  - 상태: 7.2의 상태 구간 규칙에 따름
- 엔진은 **순수 함수**(입력: 차량·규칙·기록·오늘 날짜 → 출력: 항목별 결과)로 작성해 단위 테스트한다. DB나 시간에 직접 의존하지 않는다.

#### 바. 정비 현황 대시보드
- 상단: 차량 요약(모델, 추정 주행거리, 일 평균), 계기판 업데이트 버튼.
- 경고 영역: "교체 필요" → "곧 교체" 순으로 정렬된 카드.
- 계절 정비 카드(기능 자), 보정 제안 카드(기능 아) — 해당될 때만.
- 전체 항목 목록: 항목명, 진행 막대, 남은 거리/기간, 예상 도래일, 상태 배지.
- 항목을 누르면 상세 화면(기능 사)으로 이동.

#### 사. 정비 항목 상세 / 정비 기록
- 상세: 항목 설명(무엇이고 왜 교체하는지), 적용된 주기, 계산 근거("마지막 교체 2025-12-01 · 32,000km, 주기 10,000km 또는 12개월"), 정비 기록 목록.
- 연결 버튼: "근처 정비소 보기"(기능 카), "최저가 보기"(기능 타) — 항목에 연결 키워드가 있을 때만.
- **정비 완료 기록**: 날짜(기본 오늘), 주행거리(필수), 비용(선택), 메모(선택). 저장 시:
  1. 정비 기록 추가 → 해당 항목의 다음 교체 시점이 다시 계산됨
  2. 입력한 주행거리를 **실측값**으로도 저장하고 기록과 연결(`maintenance_records.odometer_reading_id`) → 주행거리 추정 기준점 갱신(기능 라)
  3. 단, 실측 저장이 기능 아의 "감소 금지" 규칙에 걸리면(과거 날짜 기록 등) **정비 기록만 저장**하고 실측은 만들지 않으며, 그 사실을 안내한다.
- 기록 수정 시 연결된 실측도 같이 수정(규칙 위반이면 연결 해제), 기록 삭제 시 연결된 실측도 삭제한다.
- 온보딩 3단계에서 입력하는 과거 정비 이력은 **월 단위 근사값**이므로 실측으로 만들지 않는다(날짜는 해당 월 1일로 저장).

#### 아. 주행 패턴 보정 제안
- 기준 실측 = "최신 실측으로부터 180일 이내 중 가장 오래된 값"(너무 오래된 습관 반영 방지).
- 조건: 기준 실측과 최신 실측이 서로 다르고, 두 날짜 사이가 **14일 이상**. (계산식은 7.6)
- 실제 일 평균 = (최신 실측 km − 기준 실측 km) ÷ 두 날짜 사이 일수.
- 설정값과 실제값의 차이가 **20% 이상**이면 대시보드에 제안 카드를 띄운다:
  "입력하신 일 평균 31km보다 실제로는 약 38km 타고 계세요. 바꿀까요? [바꾸기] [그대로 두기]"
- "그대로 두기"를 누르면 다음 실측이 추가될 때까지 다시 띄우지 않는다.
- 실측값이 이전 실측보다 작으면(계기판 오입력) 저장을 거부한다.

#### 자. 계절 정비 안내
- 월 기준으로 계절 체크리스트를 보여준다(6.3 테이블). 연료 타입에 따라 일부 항목은 제외한다.
- 대시보드 카드: 해당 계절 동안 노출. 각 항목에 체크 표시 가능(올해 시즌 기준으로 저장).
- 계절이 시작되는 달의 첫 일일 작업 실행 때 한 번 푸시 알림(기능 차).

#### 차. 알림 (Web Push + 알림함)
- 알림 권한 요청은 **대시보드를 처음 본 뒤** 사용자가 버튼을 눌렀을 때만 한다(첫 방문 즉시 요청 금지).
- 구독 정보(push subscription)를 서버에 저장한다. 한 사용자가 기기 여러 대를 구독할 수 있다.
- 서버가 매일 1회 예약 작업(Vercel Schedules)으로 알림 대상을 계산해 발송한다(10장).
- 알림 종류:
  - `DUE_SOON`: 항목이 "곧 교체" 상태에 진입했을 때 1회
  - `OVERDUE`: 항목이 "교체 필요" 상태가 되면 첫 알림 1회, 정비 기록 전까지 직전 OVERDUE 알림으로부터 **14일 이상** 지났을 때 재알림. **주기당 총 3회**(첫 알림 + 재알림 2회)까지.
  - `SEASONAL`: 계절 시작 시 1회
  - `CALIBRATION`: 알림 없음(대시보드 카드로만)
  - 정비 기록이 없어 **추정 기준점**(7.3)으로 계산된 항목은 `DUE_SOON`만 보내고 문구를 "~할 때가 됐을 수 있어요 (기록이 없어 추정)"으로 바꾼다. `OVERDUE`는 보내지 않는다.
- **알림함**: 알림 종류가 켜져 있으면 **푸시 구독이 없어도** 알림함에는 기록된다(푸시를 못 받는 환경 대비). 읽음 처리 가능.
- 알림 설정: 종류별 켜기/끄기, 전체 끄기, 구독 기기 목록과 해제. **기본값은 모두 켜짐**(푸시 발송은 구독한 기기가 있을 때만).
- 아이폰(iOS Safari)은 **홈 화면에 추가한 PWA에서만** 푸시를 받을 수 있다. 해당 환경을 감지하면 "홈 화면에 추가하면 알림을 받을 수 있어요" 안내를 보여준다.
- "테스트 알림 보내기" 버튼: 로그인 사용자는 설정 화면에서 자기 구독 기기로 발송, 데모 사용자는 대시보드에서 발송(4.4).

### 4.2 P1 — 연결 기능 (실제 API, 가볍게)

#### 카. 주변 정비소·세차장 지도
- 카카오맵 JavaScript SDK + 장소 검색(services 라이브러리).
- 위치: 브라우저 위치 권한(Geolocation). 거부 시 주소/지역 검색창으로 대체, 기본 위치는 서울시청.
- 검색 카테고리 탭: 세차장, 정비소, 타이어, 주유소(카카오 카테고리 코드 OL7 사용), 전기차 충전소(전기차일 때 기본 탭).
- 결과: 지도 마커 + 목록(이름, 거리, 주소, 전화, 카카오맵 상세 링크).
- 정비 항목 상세에서 들어오면 해당 항목의 지도 키워드로 바로 검색한다(예: 타이어 → "타이어").

#### 타. 차량용품 최저가 비교
- 네이버 검색 API(쇼핑)를 **서버에서** 호출한다(Client Secret 보호).
- 검색어: 사용자가 입력하거나, 정비 항목에서 넘어오면 항목의 쇼핑 키워드 + 차종(예: "아반떼 CN7 에어컨필터").
- 정렬: 가격 오름차순(`sort=asc`), 결과의 `lprice`(최저가), `mallName`, 상품 링크, 이미지 표시.
- 응답 캐시 1시간(11.3).
- 화면에 "가격은 네이버 쇼핑 검색 결과 기준이며 실제와 다를 수 있음" 표기.

#### 파. 차량 소식·신차 뉴스
- 네이버 검색 API(뉴스)를 서버에서 호출.
- 탭: "내 차 소식"(모델명 검색, 예: "아반떼"), "신차 출시"("신차 출시" 검색), "자동차 일반"("자동차"). 검색창으로 자유 검색.
- 표시: 제목, 요약, 언론사 링크, 날짜. HTML 태그(`<b>` 등)와 엔티티는 서버에서 정리한다.
- 응답 캐시 30분.

### 4.3 P2 — 시간이 남으면
- 여러 차량 전환 UI
- 이메일 알림(푸시 보조 채널)
- 기상청 단기예보로 "내일 영하 — 배터리·워셔액 점검" 같은 날씨 기반 알림
- 정비 비용 통계(월별·항목별 차트)
- 다크 모드

### 4.4 데모 모드 상세 (제안)
- 시드 스크립트로 데모 사용자 1명 + 차량 1대(예: 기아 K5 2020 가솔린, 일 평균 35km 설정이지만 실측상 약 45km) + 정비 기록 6~8건 + 실측 4~5건을 생성한다. 데이터는 **오늘 날짜 기준 상대값**으로 만들어서, 언제 열어도 "교체 필요 1개, 곧 교체 2개, 보정 제안 1개"가 보이도록 한다.
- 매일 일일 작업에서 데모 데이터를 재생성해 상대 날짜를 유지한다. (배포 시 재생성은 하지 않는다: 프리뷰 배포가 프리뷰 DB 브랜치에서 각자 돌기 때문에, 데모 데이터가 없으면 처음 접속 시 만들도록 한다 — 빌더 재량)
- 데모 세션은 읽기 전용이 기본이다. 쓰기 시도 시 "데모에서는 저장되지 않아요" 안내. (임시 사본 방식은 빌더 재량)
- 데모 사용자(`users.is_demo = 1`)는 **일일 알림 작업에서 제외**한다. 데모 데이터를 매일 재생성해도 알림이 반복 생성되지 않게 하기 위함이다.
- **데모 테스트 알림**: 데모 대시보드에 "테스트 알림 받기" 버튼을 둔다. 브라우저가 만든 구독 정보를 요청 본문으로 받아 **저장하지 않고 즉시 1건만 발송**한다(`POST /api/push/demo-test`). 남용 방지를 위해 같은 endpoint는 10분에 1회로 제한한다.
- 데모 세션 구현: 데모 사용자로 로그인된 세션을 발급한다(Auth.js 세션 또는 별도 서명 쿠키 — 빌더 재량). 데모 허용 페이지는 5.1 표를 따른다.

### 5.4 디자인 원칙

## 6. 정비 규칙 데이터

### 6.1 주의
아래 수치는 국내 제조사 소모품 교환 주기 안내와 일반 정비 가이드를 참고한 **일반 참고값(초안)**이다. 구현 전 주요 제조사(현대·기아) 공식 안내와 대조해 확정하며, 화면에 "일반적인 권장 주기이며, 차량 설명서와 다를 수 있어요"를 표기한다. 가혹 조건(짧은 거리 반복, 정체 구간 위주 등) 보정은 P2다.

### 6.2 정비 항목 규칙 테이블 (초안)

## 7. 핵심 계산 로직 상세

### 7.1 용어
- `today`: 한국 시간(KST, UTC+9) 기준 날짜. Vercel Functions 는 UTC로 동작하므로(`TZ` 환경 변수에 기대지 않는다) 날짜 계산 전에 KST로 변환한다.
- `dailyKm`: 사용자 설정 일 평균 주행거리.
- `latestReading`: 가장 최근 실측(날짜, km).

### 7.2 상태 구간 규칙
각 항목에 대해 거리 기준과 기간 기준을 각각 평가하고 **더 나쁜 상태**를 택한다.

| 상태 | 거리 기준 | 기간 기준 |
|---|---|---|
| `OVERDUE` (교체 필요) | 남은 거리 ≤ 0 | 남은 기간 ≤ 0일 |
| `DUE_SOON` (곧 교체) | 남은 거리 ≤ max(주기의 10%, 500km) | 남은 기간 ≤ 30일 |
| `OK` (양호) | 그 외 | 그 외 |
| `UNKNOWN` (정보 없음) | 정비 기록이 없고 **기간 주기만 있는 항목**(배터리, 와이퍼) — 7.3 | |

### 7.3 기준점(마지막 교체 시점)이 없을 때
정비 기록이 없는 모든 항목에 적용한다(온보딩에서 "기억 안 남"을 고른 항목과 아예 묻지 않은 항목 모두 동일). 그래서 `item_baselines` 테이블은 두지 않는다.
- **거리 주기가 있는 항목**: **차량 연식 시작일(연식의 1월 1일)과 0km**를 출고 시점으로 보고, 그 이후 주기마다 교체했다고 가정해 **"다음 주기 도래 시점"**을 계산한다.
  - 예: 엔진오일(10,000km), 추정 42,775km → 마지막 가정 교체 40,000km → 다음 50,000km
  - 가정 주기 번호 `n = floor(추정 km ÷ 주기 km)`를 알림 중복 방지 키(`cycleKey = guess-{n}`)로 쓴다. 주행거리가 다음 주기로 넘어가면 새 주기로 본다.
  - 기간 주기도 함께 있으면, 기간은 출고일부터 주기 배수로 같은 방식으로 계산하고 더 나쁜 상태를 택한다.
  - 이 방식에서는 항목이 `OVERDUE`가 되지 않는다(늘 다음 주기를 가리키므로). 상태는 `OK` 또는 `DUE_SOON`.
- **기간 주기만 있는 항목**(배터리, 와이퍼): 연식 1월 1일 기준으로 가정하면 같은 연식의 모든 차가 같은 날 도래해 의미가 없으므로, 상태를 `UNKNOWN`으로 두고 "마지막 교체 시기를 알려주세요"를 표시한다. 알림 없음.
- 추정 기준으로 계산된 항목은 화면에 "기록 없음 · 추정 기준" 배지를 달고, 정비 기록을 입력하라고 유도한다.

### 7.4 예상 도래일
- 거리 기준: `today + ceil(남은 km ÷ dailyKm)`일 (남은 km ≤ 0이면 이미 도래)
- 기간 기준: `마지막 교체일 + 주기 개월`
- 예상 도래일 = 둘 중 빠른 날. 표시할 때 어느 기준인지 함께 보여준다("거리 기준" / "기간 기준").

### 7.5 계산 예시 (테스트 케이스로도 사용)
- 차량: 가솔린, dailyKm = 31, 마지막 실측 2026-11-01 · 42,000km, today = 2026-11-26
- 추정 주행거리 = 42,000 + 31 × 25 = **42,775km**
- 엔진오일 기록: 2025-12-01 · 33,300km
  - 다음: 43,300km 또는 2026-12-01
  - 남은 거리 525km → 500km와 10%(1,000km) 중 큰 값 1,000km 이하 → `DUE_SOON`
  - 거리 기준 예상일 = 11/26 + ceil(525/31)=17일 → 2026-12-13
  - 기간 기준 = 2026-12-01 → **예상 도래일 2026-12-01 (기간 기준)**
  - 남은 기간 5일 ≤ 30일 → `DUE_SOON`. 최종 `DUE_SOON`.

### 7.6 보정 제안 계산
- 실측 목록을 날짜순 정렬 → 최신 실측 `r_n`, 그로부터 180일 이내 가장 오래된 실측 `r_0`.
- `r_n.date − r_0.date ≥ 14일`이 아니면 제안 없음.
- `actual = (r_n.km − r_0.km) ÷ 일수`, `diff = |actual − dailyKm| ÷ dailyKm`.
- `diff ≥ 0.2`이고, 사용자가 이 `r_n` 이후로 "그대로 두기"를 누르지 않았으면 제안.

### 7.7 테스트해야 할 경계 사례 (최소)
- 실측 1개뿐 / 같은 날 실측 2개 / 실측값 감소 시도
- 기간 주기만 있는 항목, 거리 주기만 있는 항목
- 전기차에서 엔진오일 항목 미표시
- "기억 안 남" 항목의 기준점 가정 계산
- 연말·윤년을 넘는 기간 계산 (예: 2027-02-29 없음 → 월말 처리)
- KST 자정 직후/직전의 today 계산
- 남은 km가 정확히 0, 정확히 임계값인 경우

- **원칙**(같음): `src/lib/domain`은 DB·네트워크·현재 시간에 의존하지 않는다(오늘 날짜는 인자로 받음). 리뷰어가 가장 먼저 읽을 코드이므로 가장 깔끔하게 유지한다.

### 8.4 DB 연결 원칙
- 앱 실행 중 쿼리는 Neon 의 **풀링 연결 문자열**(`DATABASE_URL`, 호스트에 `-pooler`)을 쓴다. 마이그레이션은 **직접 연결**(`DATABASE_URL_UNPOOLED`)을 쓴다.
- 연결 객체는 모듈 범위에서 한 번 만들어 재사용한다(Vercel Functions 는 인스턴스를 재사용한다).
- **트랜잭션 필요**: 정비 완료 기록 + 실측 저장(기능 사), 데모 데이터 재생성은 한 트랜잭션이어야 한다. Neon 의 HTTP 방식 드라이버(`neon-http`)는 대화형 트랜잭션을 지원하지 않으므로, WebSocket 방식(`neon-serverless` Pool) 또는 `node-postgres` 를 쓴다. 어느 쪽인지는 빌더 재량, 조건은 "위 두 쓰기가 원자적일 것".
- Neon 무료 플랜은 일정 시간 요청이 없으면 DB 컴퓨트가 잠든다(scale to zero). 첫 요청이 수백 ms 늦어질 수 있다 → 16장.

## 9. 데이터 모델 (Neon / Postgres)

테이블과 컬럼은 Cloudflare 버전과 **같다**. Postgres 로 바뀌면서 달라지는 타입 · 제약만 정리한다.

### 9.0 Postgres 로 바뀌는 점
- 시각: `timestamptz`(UTC 로 저장). 날짜만 의미 있는 값(정비일, 실측일, 기준 날짜)은 `date`(KST 기준 날짜).
- 불리언: `boolean` (`is_demo`, 알림 설정 등). SQLite 의 0/1 대신.
- 목록: `text[]` (`fuel_types`, `excluded_fuel_types`). SQLite 의 JSON 문자열 대신.
- 고정 값 목록: `pgEnum` (연료 타입, 실측 source, 기록 source, 알림 type, 계절).
- id: `text`(UUID, `crypto.randomUUID()`). Auth.js 어댑터 표준과 맞춘다.
- nullable 컬럼이 들어간 고유키(`maintenance_rules` 의 `(item_code, fuel_type, vehicle_model_id)`): Postgres 는 기본적으로 NULL 을 서로 다른 값으로 보므로 **NULLS NOT DISTINCT** 고유 인덱스를 쓴다(Postgres 15 이상, Neon 기본 버전에서 지원). Cloudflare 버전의 `coalesce` 식 인덱스 우회가 필요 없다.
- 알림 중복 방지 INSERT: `INSERT … ON CONFLICT (dedupe_key) DO NOTHING RETURNING id` → **새로 들어간 행만** 돌려받아 그것만 발송한다.
- 시드: 차종 · 규칙 · 계절 항목 시드는 마이그레이션과 별도 스크립트(`npm run db:seed`)로, 이미 있으면 갱신(`ON CONFLICT DO UPDATE`)하는 멱등 방식.

### 9.1 인증 (Auth.js 어댑터 표준 테이블)
- `users` (id, name, email, emailVerified, image, created_at, is_demo)
- `accounts`, `sessions`, `verificationToken` — `@auth/drizzle-adapter` 의 **pg 스키마** 그대로.

### 9.2 차종·규칙 (시드, 읽기 전용)
- `vehicle_models`
  - id, maker, name, generation(nullable), year_from, year_to(nullable), fuel_types(`text[]`)
- `maintenance_items`
  - code(PK, 예: ENGINE_OIL), name, description, map_keyword(nullable), shop_keyword(nullable), sort_order
- `maintenance_rules`
  - id, item_code(FK), fuel_type, vehicle_model_id(nullable, 차종 예외용), interval_km(nullable), interval_months(nullable)
  - 고유키: (item_code, fuel_type, vehicle_model_id) `NULLS NOT DISTINCT`
- `seasonal_items`
  - id, season(SPRING/SUMMER/FALL/WINTER), label, excluded_fuel_types(`text[]`), sort_order

### 9.3 사용자 데이터
- `vehicles`
  - id, user_id(FK), vehicle_model_id(FK, nullable), custom_model_name(nullable), model_year, fuel_type, nickname, daily_km, created_at, updated_at
- `odometer_readings` (실측)
  - id, vehicle_id(FK), date, km, source(ONBOARDING/MANUAL/MAINTENANCE), created_at
  - 제약: 같은 차량에서 날짜가 더 늦은데 km가 더 작은 값은 저장 불가(애플리케이션 검증)
- `maintenance_records`
  - id, vehicle_id(FK), item_code(FK), date, km, cost(nullable), memo(nullable), odometer_reading_id(FK, nullable — 기능 사에서 함께 만든 실측), source(ONBOARDING/MANUAL), created_at
- `calibration_dismissals`
  - vehicle_id(PK), dismissed_at_reading_id — "그대로 두기"를 누른 시점의 최신 실측. 그 실측이 삭제되면 행도 삭제(`ON DELETE CASCADE`).
- `seasonal_checks`
  - vehicle_id, season_key(예: 2026-WINTER), seasonal_item_id, checked_at
- 회원 탈퇴 시 전부 삭제: `users` 를 지우면 나머지가 `ON DELETE CASCADE` 로 지워지게 FK 를 건다.

### 9.4 알림
- `push_subscriptions`
  - id, user_id, endpoint(UNIQUE), p256dh, auth, user_agent, created_at, last_success_at
- `notification_prefs`
  - user_id(PK), due_soon(bool), overdue(bool), seasonal(bool), all_off(bool)
- `notifications` (알림함 + 중복 방지 기록)
  - id, user_id, vehicle_id, type(DUE_SOON/OVERDUE/SEASONAL/TEST), item_code(nullable), dedupe_key(UNIQUE), title, body, url, created_at, read_at(nullable)
  - `dedupe_key` 예: `DUE_SOON:{vehicleId}:{itemCode}:{cycleKey}`, `OVERDUE:{vehicleId}:{itemCode}:{cycleKey}:{n}`, `SEASONAL:{vehicleId}:2026-WINTER`
  - `cycleKey` = 해당 항목의 마지막 정비 기록 id. 기록이 없으면 `guess-{n}`(7.3) → 정비 기록이 추가되거나 가정 주기가 넘어가면 새 주기로 간주되어 다시 알림 가능
- `demo_push_sends` (데모 테스트 알림 남용 방지, 4.4): endpoint 의 해시(PK), last_sent_at. 10분 안에 같은 endpoint 면 거부. 구독 정보 자체는 저장하지 않는다.

### 9.5 인덱스
- `odometer_readings(vehicle_id, date)`, `maintenance_records(vehicle_id, item_code, date)`, `notifications(user_id, created_at)`, `push_subscriptions(user_id)`

## 10. 알림 시스템 상세

### 10.1 구독 흐름
1. 사용자가 "알림 받기"를 누름 → `Notification.requestPermission()`
2. 허용 시 서비스 워커 등록(`/sw.js`) → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: VAPID 공개키 })`
3. 구독 정보를 `POST /api/push/subscribe`로 저장(로그인 사용자 기준). 같은 endpoint가 있으면 갱신.
4. 해제 시 `pushSubscription.unsubscribe()` + `DELETE /api/push/subscribe`.

### 10.2 일일 작업 (Vercel Schedules, 매일 KST 09:00 ~ 09:15)
```
for each 데모가 아니고 전체 끄기가 아닌 사용자의 차량:   (푸시 구독 유무와 무관)
    결과 = 규칙엔진(차량, 규칙, 기록, 실측, today)
    for each 항목 in 결과 (해당 알림 종류가 켜진 것만):
        if 상태 == DUE_SOON  → 후보(DUE_SOON, cycleKey)
        if 상태 == OVERDUE   → 이 주기의 기존 OVERDUE 알림 수 k 조회
                               k == 0 → 후보(OVERDUE, n=0)
                               0 < k < 3 이고 마지막 OVERDUE 알림이 14일 이상 전 → 후보(OVERDUE, n=k)
    if 오늘이 계절 시작 월이고 이번 시즌 알림 기록 없음 → 후보(SEASONAL)
    후보마다 INSERT … ON CONFLICT (dedupe_key) DO NOTHING RETURNING  ← 중복 방지의 핵심
    새로 INSERT된 알림만 → 사용자의 모든 구독 기기로 푸시 발송 (web-push)
       - 410/404 응답 → 해당 구독 삭제
       - 그 외 실패 → 로그만 남기고 계속 (알림함에는 이미 기록됨)
       - 성공 → last_success_at 갱신
같은 사용자의 알림이 여러 개면 한 번의 푸시로 묶는다 ("정비 알림 3건: 엔진오일 외 2건")
데모 데이터 갱신 (한 트랜잭션: 지우고 다시 만들기)
```
- OVERDUE 재알림 간격은 "진입일"이 아니라 **직전 OVERDUE 알림의 생성 시각**으로 계산한다. 그래서 하루 실행이 빠지거나 실측 입력으로 과거에 이미 도래한 것으로 바뀌어도 알림이 누락되지 않는다.
- 하나의 대시보드에서 기한이 바뀌는 경우(실측·일 평균 수정)에도 dedupe 키가 같으면 다시 보내지 않는다.

**Vercel Schedules 때문에 정해 두는 것**
- **호출 방식**: Schedules 가 `POST /api/internal/run-daily` 를 호출하면서 `Authorization: Bearer <CRON_SECRET>` 헤더를 붙인다. 경로는 이 값을 타이밍 안전 비교로 검사하고, 없거나 틀리면 401. `CRON_SECRET` 이 설정되지 않았으면 항상 401(열린 채로 배포되지 않게).
- **실행 시각 오차**: Hobby 플랜은 오차 구간(jitter)이 15분으로 고정이라 09:00~09:15 사이에 실행된다. 알림 문구에 시각을 넣지 않으므로 영향 없음.
- **중복 실행**: Schedules 는 같은 회차를 두 번 보낼 수 있다고 문서에 적혀 있다. 알림은 `dedupe_key` 로 한 번만 생기고, 데모 재생성은 트랜잭션 안의 "지우고 다시 만들기"라 두 번 돌아도 결과가 같다. 요청 헤더의 실행 ID(`ce-id`)를 로그에 남긴다.
- **누락**: 실패한 호출은 재시도되지 않는다. 하루가 빠져도 다음 날 실행에서 DUE_SOON · OVERDUE 후보가 다시 계산되어 하루 늦게 나간다(OVERDUE 간격은 직전 알림 기준이라 회차 계산이 틀어지지 않는다). 연속 실패를 알 수 있게 마지막 성공 시각을 `/api/health` 응답에 포함한다(빌더 재량).
- **실행 시간**: 함수 최대 실행 시간 안에 끝나야 한다. route 에 `maxDuration` 을 지정하고, 사용자별 푸시 발송은 `Promise.allSettled` 로 병렬 처리한다. 포트폴리오 규모(사용자 수십 명 이하)에서는 한 번의 실행으로 충분하다. 사용자가 늘면 Vercel Queues(Schedules 의 queue 대상)로 나누는 것이 다음 단계라고 README 에 적는다.

### 10.3 일일 작업 테스트
- Cloudflare 버전처럼 테스트 전용 경로를 따로 둘 필요가 없다. **운영 호출 경로가 곧 HTTP 경로**이므로 같은 경로를 직접 호출해 확인한다.
- 로컬: `curl -X POST -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/internal/run-daily`
- 프리뷰: 프리뷰 브랜치의 Schedules 는 **비활성으로 시작**하므로 그대로 둔다(프리뷰 DB 에서 매일 알림이 나가지 않게). 필요하면 프리뷰 환경의 `CRON_SECRET` 으로 직접 호출한다.
- 운영: Vercel 대시보드의 수동 실행 또는 위 curl.

### 10.4 알림 내용 예시
- 제목: "엔진오일 교체 시기가 다가와요" / 본문: "약 500km 남았어요 · 12/1 예상" / 클릭: `/maintenance/ENGINE_OIL`
- 제목: "브레이크액 교체 시기가 지났어요" / 본문: "교체한 지 24개월이 지났어요" / 클릭: `/maintenance/BRAKE_FLUID`
- 제목: "겨울철 차량 점검 시즌이에요" / 본문: "배터리, 부동액, 워셔액을 확인해 보세요" / 클릭: `/dashboard`

### 10.5 서비스 워커
- `push` 이벤트: payload(JSON: title, body, url)로 `showNotification`.
- `notificationclick`: 이미 열린 탭이 있으면 그 탭으로 이동, 없으면 새 창으로 `url` 열기.
- PWA `manifest.webmanifest`: 이름, 아이콘(192/512), `display: standalone` — iOS 푸시 조건.

## 11. 외부 API 연동

### 11.1 목록

| 용도 | API | 호출 위치 | 키 보관 |
|---|---|---|---|
| 지도·장소 검색 | 카카오맵 JavaScript SDK (+services) | 브라우저 | JS 키 (공개, 카카오 콘솔에서 **도메인 제한**: 운영 도메인 + localhost) |
| 로그인 | 카카오 로그인, 구글 OAuth | 서버(Auth.js) | Vercel 환경 변수 (Sensitive) |
| 최저가 | 네이버 검색 API — 쇼핑 | 서버 | Vercel 환경 변수 (Client ID/Secret) |
| 뉴스 | 네이버 검색 API — 뉴스 | 서버 | Vercel 환경 변수 |
| 푸시 | Web Push (VAPID) | 서버 | VAPID 개인키: Vercel 환경 변수 / 공개키: `NEXT_PUBLIC_` 변수 |

- 각 API의 일일 호출 한도·이용 약관(출처 표기 등)은 구현 시 콘솔에서 확인해 README에 정리한다.

### 11.2 실패 처리
- 서버 프록시(`/api/shop`, `/api/news`)는 외부 API 실패 시 `502`와 사용자용 메시지를 반환하고, 화면은 대체 문구를 보여준다. 대시보드(핵심 기능)는 외부 API에 **의존하지 않는다**.
- 외부 응답은 zod로 필요한 필드만 검증·추출한 뒤 내려준다(HTML 태그 제거 포함).

### 11.3 캐시
- 서버에서 네이버를 부를 때 `fetch(url, { headers, next: { revalidate: 3600 } })`(쇼핑 1시간), 뉴스는 `1800`(30분). 같은 요청(URL 단위, 검색어가 URL 에 들어감)은 Vercel 의 데이터 캐시에서 돌려준다. 배포가 바뀌어도 캐시는 유지된다.
- 조건: **실패 응답은 캐시하지 않는다.** (오류가 1시간 동안 굳지 않게. 구현 시 Next.js 가 실패 응답을 캐시하는지 확인하고, 하면 실패 때 캐시를 건너뛰는 방식으로 짠다.)
- 캐시 API 형태(`fetch` 의 `revalidate` 또는 `'use cache'` + `cacheLife`)는 빌더 재량. 조건은 검색어 단위 · 쇼핑 1시간 · 뉴스 30분.

## 12. 인증 · 보안 · 개인정보

- 모든 사용자 데이터 접근은 **세션의 user_id로 소유권을 검사**한다(다른 사람 vehicle_id 접근 차단). Server Action마다 공통 헬퍼로 강제.
- 모든 입력은 zod로 검증: 주행거리(0 ~ 2,000,000), 일 평균(1 ~ 500), 날짜(미래 불가), 비용(0 이상), 메모 길이(500자).
- 비밀값(OAuth 비밀키, 네이버 Secret, VAPID 개인키, `CRON_SECRET`, `AUTH_SECRET`)은 **Vercel 환경 변수**(Sensitive 표시, 환경별로 따로)에만 둔다. 로컬은 `vercel env pull` 로 받은 `.env.local`. `.env*` 는 `.gitignore`, 저장소에는 값 없는 `.env.example` 만.
- 내부 작업 경로(`/api/internal/*`)는 `CRON_SECRET` 비교(타이밍 안전 비교) 필수.
- 프록시 경로(`/api/shop`, `/api/news`)는 남용 방지를 위해 검색어 길이 제한(50자) + 캐시. (필요하면 Vercel Firewall 의 Rate Limiting 규칙 추가 — 빌더 재량)
- 데모 계정은 쓰기 차단.
- **프리뷰 배포 보호**: 프리뷰 DB 브랜치는 운영 DB 를 복사해 만들어지므로(13.1) 실제 사용자 데이터가 들어 있다. 프리뷰 주소는 **Vercel Deployment Protection(Vercel Authentication)을 켜서** 본인만 열 수 있게 한다.
- 개인정보: 이메일·이름(소셜 로그인 제공값), 차량 정보, 위치(저장하지 않음 — 지도 검색에만 브라우저에서 사용). 개인정보 처리 안내 페이지(간단한 텍스트) 제공, 회원 탈퇴 시 전부 삭제. 데이터 저장 위치(Neon 리전)를 안내 페이지에 적는다.

## 13. 배포 · CI/CD (Vercel Git 연동 + GitHub Actions)

### 13.1 환경
- **production**: `main` 브랜치 → Vercel 운영 배포(`*.vercel.app` 또는 사용자 도메인). DB 는 Neon 의 기본 브랜치(`main`). Schedules 활성.
- **preview**: PR 브랜치에 push 할 때마다 Vercel 프리뷰 배포. Neon 연동이 **Git 브랜치마다 DB 브랜치**를 만든다(그 시점 운영 DB 의 복사본, 복사 비용 없음). 프리뷰는 그 DB 브랜치의 연결 문자열을 받는다. Schedules 비활성. PR 이 닫히면 DB 브랜치를 지우도록 연동을 설정한다(설정 이름은 구현 시 확인).
- **local**: `next dev` + Neon 의 개인 개발 브랜치(`dev`). `vercel env pull` 로 `.env.local` 을 받는다. 로컬 Postgres(도커)는 쓰지 않는다(설치할 것이 없도록).
- 함수 리전은 Neon 프로젝트 리전과 **같은 곳**으로 맞춘다(16장).

### 13.2 흐름

PR:
1. GitHub Actions `ci.yml`: checkout, Node 설정, 의존성 설치(캐시) → lint → `tsc --noEmit` → Vitest(PGlite 로 DB 통합 테스트까지) → `next build`. **DB 연결이나 Secrets 가 필요 없다.**
2. 동시에 Vercel 이 프리뷰 빌드: 프리뷰 DB 브랜치에 마이그레이션 → 빌드 → 프리뷰 주소를 PR 에 코멘트(Vercel 기본 기능).
3. (선택) 프리뷰 배포가 끝나면 Playwright E2E 를 프리뷰 주소에 실행(14장).

main 병합:
1. GitHub 의 **main 브랜치 보호**로 `ci.yml` 통과 + PR 을 거쳐야만 병합되게 한다. → 운영 배포는 항상 CI 를 통과한 코드다. (Vercel 쪽 기능에 기대지 않고 GitHub 설정으로 해결)
2. Vercel 운영 빌드: 운영 DB 에 마이그레이션 → 빌드 → 배포.
3. 배포가 끝나면 Vercel 이 GitHub 에 `deployment_status` 이벤트를 보낸다 → `smoke.yml` 이 운영 주소의 `/` 와 `/api/health` 가 200 인지 확인. 실패하면 Vercel **Instant Rollback** 으로 직전 배포로 되돌린다(수동).

### 13.3 마이그레이션은 빌드 단계에서
- `package.json` 에 `"vercel-build": "drizzle-kit migrate && next build"` 를 둔다(Vercel 은 이 스크립트가 있으면 이것으로 빌드한다). 마이그레이션은 `DATABASE_URL_UNPOOLED` 로 연결한다.
- 프리뷰 빌드는 프리뷰 DB 브랜치에, 운영 빌드는 운영 DB 에 적용된다. 연결 문자열이 환경별로 달라서 저절로 그렇게 된다.
- **주의 1**: 마이그레이션이 성공한 뒤 빌드가 실패하면 DB 가 코드보다 앞서 있게 된다. 그래서 **마이그레이션은 추가형만** 쓴다(테이블 · 컬럼 추가, nullable 로 추가). 컬럼 삭제 · 이름 바꾸기는 두 번의 배포로 나눈다(새 컬럼 추가·코드 전환 → 다음 배포에서 옛 컬럼 삭제).
- **주의 2**: Instant Rollback 은 코드만 되돌리고 DB 는 되돌리지 않는다. 위 추가형 규칙 덕분에 직전 코드도 새 스키마에서 동작한다.
- 시드(`npm run db:seed`)는 멱등이므로 빌드 단계에서 마이그레이션 뒤에 같이 돌려도 된다(빌더 재량).

### 13.4 환경 변수
- **GitHub Actions Secrets**: 없음. CI 는 DB 없이 돌고, 배포는 Vercel 이 한다. (Cloudflare 버전의 `CLOUDFLARE_API_TOKEN` · `CLOUDFLARE_ACCOUNT_ID` 가 필요 없다.)
- **Vercel 환경 변수** (Production / Preview / Development 별로):
  - Neon 연동이 자동으로 넣는 것: `DATABASE_URL`, `DATABASE_URL_UNPOOLED` (프리뷰는 브랜치별 값)
  - 직접 넣는 것: `AUTH_SECRET`, `AUTH_KAKAO_ID/SECRET`, `AUTH_GOOGLE_ID/SECRET`, `NAVER_CLIENT_ID/SECRET`, `VAPID_PRIVATE_KEY`, `CRON_SECRET`(16자 이상 무작위)
  - 공개 변수: `NEXT_PUBLIC_KAKAO_MAP_KEY`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`
- `AUTH_URL` 은 넣지 않는다. Auth.js 가 Vercel 에서는 요청 호스트를 자동으로 믿는다. (Cloudflare 버전에서 겪은 `redirect_uri` 의 http/https 문제가 없다.)
- 환경 변수를 바꾸면 **재배포해야 반영된다.** `CRON_SECRET` 도 마찬가지(Schedules 는 현재 배포에 저장된 값을 보낸다).

### 13.5 Schedules 설정 (`vercel.json`)
```json
{
  "schedules": {
    "run-daily": {
      "schedule": "0 9 * * *",
      "timezone": "Asia/Seoul",
      "path": "/api/internal/run-daily",
      "requestMethod": "POST"
    }
  }
}
```
- Hobby 는 `jitter` 가 15로 고정이라 적지 않는다(다른 값은 거부됨).
- **대체안**: Schedules 는 Beta 다. 막히거나 바뀌면 기존 Cron Jobs 로 바꾼다: `{ "crons": [{ "path": "/api/internal/run-daily", "schedule": "0 0 * * *" }] }` (UTC 00:00 = KST 09:00, GET 으로 호출, Hobby 는 하루 1회 · 정한 시각부터 최대 59분 늦게). 이때 경로가 GET 도 받게 한다. **두 설정을 동시에 두지 않는다**(같은 회차에 두 번 실행됨).
- **GitHub Actions의 schedule 기능은 쓰지 않는다**(Cloudflare 버전과 같은 이유: 60일 비활동 시 자동 비활성화).

### 13.6 프리뷰에서의 로그인 · 지도
- 프리뷰 주소는 배포마다 바뀌어서 카카오 · 구글 OAuth 의 redirect URI 와 카카오맵 도메인 제한에 미리 등록할 수 없다.
- 결정(작성자 판단): 프리뷰에서는 **데모 모드로 확인**하고, 소셜 로그인 · 지도는 운영과 로컬에서 확인한다. 프리뷰에서도 로그인이 필요해지면 Auth.js 의 `AUTH_REDIRECT_PROXY_URL`(운영 주소를 거쳐 돌아오게 하는 기능)을 쓴다 — 빌더 재량.

## 14. 테스트 전략

| 수준 | 대상 | 도구 | 기준 |
|---|---|---|---|
| 단위 | `src/lib/domain/*` (추정, 규칙 엔진, 상태 구간, 보정, 계절, KST 날짜) | Vitest | 7.5 예시 + 7.7 경계 사례 전부, 도메인 커버리지 90% 이상 |
| 단위 | 알림 후보 계산·dedupe_key 생성 | Vitest | DUE_SOON 1회, OVERDUE 직전 알림 14일 후 재알림·주기당 총 3회, 정비 기록 후 재알림 가능, 추정 항목은 DUE_SOON만, 데모 사용자 제외, 구독 없어도 알림함 기록 |
| 통합 | Server Action 소유권 검사, 실측 감소 거부, 정비 기록 + 실측 트랜잭션 | Vitest + **PGlite** (같은 마이그레이션 SQL 적용) | 타인 차량 접근 시 거부, 중간 실패 시 둘 다 저장 안 됨 |
| 통합 | 일일 작업 경로 | Vitest + PGlite | `CRON_SECRET` 없음/틀림 → 401, **같은 날 두 번 호출해도 알림 1건** (Schedules 중복 실행 대비) |
| E2E | 데모 진입 → 대시보드 → 항목 상세 → 지도 화면으로 이동 | Playwright | 프리뷰 배포 주소에 실행(프리뷰 보호는 자동화용 우회 토큰으로 통과). 외부 API 결과는 검증하지 않고 화면 이동만 확인 |
| 수동 | 실제 기기 푸시 수신(안드로이드 Chrome, 데스크톱 Chrome, iOS PWA) | — | 주차별 체크리스트 |

- PGlite 는 실제 Postgres 를 WASM 으로 돌린 것이라 `NULLS NOT DISTINCT`, `ON CONFLICT`, `text[]` 같은 Postgres 문법을 그대로 검증할 수 있다. 운영 드라이버(Neon)와 테스트 드라이버(PGlite)만 다르고 Drizzle 코드는 같다.
- E2E 대상(프리뷰 주소 vs CI 안의 로컬 빌드)은 빌더 재량. 로컬 빌드로 돌린다면 PGlite 를 DB 로 쓰는 테스트 모드가 따로 필요하다.

## 17. 검토한 접근 방식 (Approaches)

### 17.1 전체 구조 (Cloudflare 버전과 같음)
- **가. Next.js 하나로 풀스택 — 선택.** Route Handler·Server Action이 백엔드, 저장소 하나. 백엔드 로직이 직접 작성한 코드로 남아 포트폴리오 목적에 맞고, 1인 4주에 현실적이다.
- 나. Next.js + Supabase에 백엔드 위임 — 기각. 핵심 로직이 서비스 설정 속으로 들어가 "백엔드를 직접 구축"하려는 목적과 어긋난다.
- 다. Next.js 프론트 + 별도 백엔드 서버(NestJS 등) — 기각. 서버 두 개의 구축·배포 비용 때문에 4주 안에 핵심 기능 완성도가 떨어질 위험이 크다.

### 17.2 배포 흐름 (이 문서에서 새로 고른 것)
- **가. Vercel Git 연동이 배포를 맡음 — 선택 (사용자 결정).** main → 운영, PR → 프리뷰 + 프리뷰 DB 브랜치. GitHub Actions 는 검사와 배포 후 스모크만. Cloudflare 버전과 가장 다른 방식이라 비교 자료로서 의미가 크고, PR 마다 앱과 DB 가 함께 프리뷰되는 흐름을 보여줄 수 있다. 대가: "CD 를 직접 짰다"는 포인트가 약해진다.
- 나. GitHub Actions 가 배포까지 맡음(검사 → 마이그레이션 → `vercel deploy --prebuilt --prod`) — 기각. 두 문서의 차이가 플랫폼 하나로 좁혀지는 장점은 있지만, Vercel 의 자동 프리뷰를 거의 안 쓰고 토큰 · 워크플로 관리가 늘어난다.

### 17.3 실행 · DB (사용자 결정)
- **순정 Next.js**: Vercel 이 Next.js 를 기본으로 지원하므로 vinext 같은 빌드 도구가 필요 없다.
- **Neon Postgres**: Vercel Marketplace 의 기본 Postgres 이고, 연동이 프리뷰 DB 브랜치를 만들어 준다. 검토한 대안 — Turso(libSQL, SQLite 호환): Cloudflare 버전의 스키마를 거의 그대로 쓸 수 있어 비교 시 DB 차이가 사라지지만, Vercel 에서 가장 일반적인 선택을 보여주는 쪽을 택했다.

### 17.4 작성자 판단으로 정한 것
- ORM 은 **Drizzle 유지**(Prisma 아님): 비교할 때 차이가 플랫폼에서만 나도록.
- 예약 작업은 **Vercel Schedules**(기존 Cron Jobs 아님): 시간대(KST)를 지정할 수 있고 Hobby 오차가 15분으로 Cron Jobs(최대 59분)보다 작다. Beta 라서 Cron Jobs 를 대체안으로 둔다.
- 푸시는 **web-push**: Node 런타임이라 Web Crypto 전용 라이브러리가 필요 없다.
- 캐시는 **Next.js 데이터 캐시**: Workers Cache API 에 해당하는 Vercel 의 기본 수단.
- 테스트 DB 는 **PGlite**: Cloudflare 버전의 `node:sqlite` 와 같은 발상(설치 없이 같은 마이그레이션 SQL 적용).

## 18. 결정 사항 정리

### 18.1 사용자가 결정한 것
- (Cloudflare 버전에서 이어받음) 목적: 포트폴리오, 실제 데이터 최대한 사용 / 중심 기능: 내 차 맞춤 정비 시기 추천 + 알림 / 주행거리: 일/월 평균 입력 + 주행 습관 계산기로 자동 추정 / 1인, 한 달 / Next.js 풀스택
- (이 문서) **비교용** 문서, 기존 코드 이전이 아니라 **처음부터 Vercel 로 만든다는 가정**
- (이 문서) 배포: **Vercel**, 실행: **순정 Next.js**, DB: **Neon Postgres**
- (이 문서) CD: **Vercel Git 연동** (GitHub Actions 는 검사)

### 18.2 작성자가 제안한 것 (검토 시 수정 가능)
- 서비스 내용(기능 · 계산 · 알림 규칙 · 데모 모드 · 규칙 수치)은 Cloudflare 버전 18.2 를 그대로 이어받는다.
- Drizzle 유지, Vercel Schedules(Beta, 대체안 Cron Jobs), `web-push`, Next.js 데이터 캐시, PGlite 테스트
- 마이그레이션은 `vercel-build` 단계에서, **추가형만**
- 운영 배포 전 CI 통과는 **main 브랜치 보호**로 강제, 배포 후 스모크는 `deployment_status` 이벤트로
- 프리뷰 Deployment Protection 필수, 프리뷰는 데모 모드로 확인(13.6), 프리뷰 Schedules 비활성
- 로컬 개발은 Neon `dev` 브랜치(도커 없음), 함수 리전을 Neon 리전에 맞춤
- 일일 작업은 운영 경로를 그대로 테스트(별도 테스트 경로 없음), 중복 호출 대비 테스트
- 데모 데이터는 일일 작업에서 재생성 + 없으면 첫 접속 때 생성(프리뷰 DB 대비)
- 데모 테스트 알림 10분 제한은 `demo_push_sends` 테이블로

### 18.3 빌더 재량 (설계에 영향 없는 세부)
- (이어받음) UI 컴포넌트 라이브러리, 아이콘, 색상 토큰의 세부 값 / 데모 쓰기 차단 방식 / 차종 시드의 정확한 모델 목록
- Neon 드라이버 방식(`neon-serverless` Pool 또는 `node-postgres`) — 조건: 8.4 의 쓰기가 원자적일 것
- 캐시 API 형태(`fetch` revalidate 또는 `'use cache'`) — 조건: 11.3
- 프리뷰 OAuth 를 `AUTH_REDIRECT_PROXY_URL` 로 열지 여부
- Vercel Firewall Rate Limiting 규칙 추가 여부
- E2E 실행 대상(프리뷰 주소 또는 로컬 빌드)
- 시드를 빌드 단계에서 같이 돌릴지 여부
- `/api/health` 에 일일 작업 마지막 성공 시각 포함 여부
